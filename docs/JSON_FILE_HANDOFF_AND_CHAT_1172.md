# 1.17.2 / Agent 0.14.0：JSON 修复、文件交接与多模型等待

基于 1.17.1 修改；继续保留 GLM 手动选择 `glm-5.3-flash` 后复用同源网页、不在每轮自动刷新的行为。本次改动不调用远端模型纠正 JSON，不实现验证码绕过或滑块自动求解。

## 1. 本地 JSON 修复与问题样本

此次 `events1.jsonl` 的一个完整助手回复在 `final.answer` 内出现 4 处非法 `\_`，例如 `realtime\_query`，严格 JSON 解析报 `Invalid \\escape`。日志分片重组、按正文哈希去重后得到 1 个样本，离线回放通过。原始正文、规范化协议及展示用 Markdown 分开保存；展示层换行处理不修改命令参数。

解析优先严格 JSON。失败后执行有限、可组合的本地修复：去除 BOM 或包住整个协议的 JSON 围栏；转义字符串内部的原始换行、回车、制表及其他控制字符；修复字符串外已知 Markdown 数组括号污染；去除有限数量的尾逗号；最后按协议字段检查非法 Markdown 标点转义。以上变换可组合，解决非法转义、换行和尾逗号同时出现的情况。

`final.answer` 允许相应 Markdown 标点纠正；文件工具只保留已有的狭窄兼容规则（已知文件工具路径中的 `\_`、files.write 正文中的 `\*`）。不会全局删除反斜杠或修改 shell 命令、argv、URL、工具名称等字段。合法 JSON 中原有的双重转义不再次按坏 JSON 重写。无法证明安全的输入、重复键、未闭合/截断协议、多个协议对象仍拒绝；不会用 eval，也不会猜测缺失的命令或括号。

每个任务默认保留修复成功与失败的样本：

```text
desktop-agent/.runtime/runs/<run_id>/
  json-repair/
    <序号>-step-<步骤>-<随机编号>/
      original.invalid.json   # 精确保留进入解析器的助手正文；故意可能不是合法 JSON
      normalized.json         # 仅解析成功时生成的规范化协议
      report.json             # 错误位置、修复项、哈希、算法版本与关联响应
```

实际根目录由 Agent `runtime_dir` 决定；相对配置路径以 Agent 配置文件目录为基准。文件名带独立编号，不覆盖旧样本；每轮最多 512 个样本。样本写入失败会记录 `model.json_debug_save_failed`，不会把失败的协议变成可执行动作。

## 2. 服务器响应以文件交给本地 Agent

Agent 配置默认值：

```json
{
  "response_delivery": "file",
  "save_problem_json": true
}
```

这是现有 `desktop-agent/agent.config.json` 的新增字段示意，不要用此片段覆盖其他配置。已有配置未包含这些字段时自动使用默认值。例子也已更新到 `desktop-agent/config.example.json`。

默认数据流：

```text
HTTP 响应
  → 客户端在本地预留的私有目录保存 HTTP 正文
  → 提取 choices[0].message.content，保存 reply.txt 与摘要元数据
  → 将本进程签发的 ResponseFile 引用交给 Agent
  → Agent 打开本地文件，核对路径、类型、权限、字节数与 SHA-256
  → 读取正文 → 本地解析/纠正 JSON → 原有意图与工具权限检查 → 执行动作
```

这里读文件的是**本地 Agent 运行器**，不是让 GLM 网页模型访问本地路径，也不要求服务器接收文件或改变 API 协议。远端返回的任意路径字符串不能伪装成可信文件引用，文件内容仍是模型产生的不可信协议；原有工具权限、工作区范围和副作用检查不变。

新增目录：

```text
desktop-agent/.runtime/runs/<run_id>/
  responses/<response_id>/
    http-response.body       # 有上限的 HTTP 响应原文，可能本来就是坏 JSON
    http-metadata.json       # HTTP 状态、大小、哈希及截断标志，不保存请求认证头
    reply.txt                # 助手原始正文
    response.json            # 本地引用、编码、大小、哈希与创建时间
```

常规 HTTP 正文按客户端响应上限保存；超限正文和 HTTP 错误正文只保留有界样本，并标明截断。助手协议最多 512 Ki 字符。目录权限为 0700、文件为 0600；拒绝符号链接、不符合预期的硬链接或权限、大小及哈希变化。每个内存引用只能消费一次。

创建目录失败时不发送请求；HTTP 请求完成后落盘失败或 Agent 校验/读回失败时停止本轮动作，不静默切回 inline，不自动重新发送。HTTP 外层已损坏时仍保留有界原文并报错，不猜测响应封装。

从父项目目录使用：

```bash
# 默认已经启用 file；这里显式列出便于核验
./desktop-agent/run.sh run "你好" --model glm --response-delivery file

# 兼容原来的内存字符串交接方式
./desktop-agent/run.sh run "你好" --model glm --response-delivery inline

# 关闭问题 JSON 样本归档（响应文件策略单独控制）
./desktop-agent/run.sh run "你好" --model glm --no-save-problem-json
```

直接把 `FusionClient` 作为 Python 库使用时，构造器仍默认 inline，以兼容旧调用方；CLI 和交互模式按 Settings 默认启用 file。库调用需要同时向客户端和 Runtime 注入同一个 ResponseStore。

### 隐私与保留策略

精确原文不做正文脱敏，否则可能无法重现 JSON 错误；其中可能包含聊天、文件内容、代码和个人信息。请勿公开上传整个 `responses/` 或 `json-repair/`，需要共享时先检查内容。

`--log-metadata-only` 下，新增加的响应/纠错归档只保留元数据，交接用 `reply.txt` 在校验读完后删除，不持久保存 HTTP 原文。**这不删除既有的任务 transcript、状态和最终结果**，也不追溯删除过去的归档；进程异常退出仍可能遗留临时交接文件。默认内容保留模式不自动按天清理，长期使用请自行管理 `.runtime/runs/` 的容量。

## 3. 离线回放

以下命令仅使用本地 Python 解析器，不启动父服务、不请求模型、不执行工具动作。输出目录必须是新目录，避免覆盖现场；输入文件最大 32 MiB，最多回放 512 个去重样本。JSONL 的缺失或重复分片、截断以及超限会给出警告，不把不完整分片拼成可执行协议。

```bash
# 在父项目根目录执行，无需 npm 依赖
PYTHONPATH=desktop-agent/src python3 -m fusion_agent.repair_json \
  /绝对路径/events1.jsonl --events \
  --output-dir /绝对路径/新的回放目录

# 也可以走 Agent 入口
./desktop-agent/run.sh repair-json /绝对路径/events1.jsonl \
  --events --output-dir /绝对路径/另一新的回放目录

# 单个原始问题协议
./desktop-agent/run.sh repair-json /绝对路径/original.invalid.json \
  --output-dir /绝对路径/新的单样本目录

# 从保存的标准 HTTP 封装提取助手正文（外层必须是完整 JSON）
./desktop-agent/run.sh repair-json /绝对路径/http-response.body \
  --http-response --output-dir /绝对路径/新的HTTP回放目录
```

输出 `replay-summary.json`，每个样本保存原始正文、规范化协议和报告；final 类型另有展示用 `answer.md` 与 `display-normalizations.json`。回放不会跟随日志正文声称的文件路径。退出码 0 表示所有样本通过且没有警告，2 表示失败或存在警告。

## 4. 多模型对话：共同截止时间与全部完成屏障

设置位置：**设置 → 生成参数 → 多模型候选回答总等待（秒）**。默认 60 秒，可设置 15–1200 秒，对应父配置：

```json
{
  "chat": {"timeout_seconds": 60},
  "allow_partial": false
}
```

该片段只展示对应字段。缺少 `chat` 的旧配置自动获得 60 秒默认值；已有配置的其他字段不覆盖。请确保没有人为开启“允许部分结果”，以保持两路全部成功才整合。

`web-fusion` 的所有候选共享一个截止时间，不是第一个模型等 60 秒再给第二个另等 60 秒。预算从当前排队任务开始执行候选阶段算起，涵盖访问限速、加载、输入队列、提交、生成、采集、恢复和人工验证等待。它不包含此前队列等待，也不包含之后的整合阶段。若限速设得超过 60 秒，请相应提高此预算。

“完成”的条件是本路完整回答已经提取且原文写入磁盘。后台保留 gather 屏障；只有全部成功并保存后才能发出 `fusion_started`，先返回的一路不能提前触发整合。某路失败或超时，其他路仍等到终态；默认不整合、不使用半截文本、不自动重发，已成功原文仍留在父应用数据目录的 `runs/<request_id>/`。只有显式允许部分结果时，才在各路结束后整合成功来源，并标明缺失来源。

**整合阶段有独立超时**，继续使用现有 `fusion.timeout_seconds`（默认 600 秒），网页整合还保留现有恢复预算。`model: "glm"`、`"chatgpt"` 等单模型 API/Agent 请求保持原有生成等待参数（默认生成 600 秒），不被多模型候选的 60 秒设置截断。

### 同步状态显示

统一对话下方新增逐模型状态行，显示排队、准备、填入、已发送、服务端响应、生成、提取、原文已保存、超时/失败/取消、人工验证等待等阶段。示例：

```text
候选回答：1/2 已完成 · 等待 GLM
ChatGPT    原文已保存
GLM        生成中
```

进度通过本地请求专属编号以约 500 ms 间隔轮询，避免旧任务或整合阶段重置候选状态。它是阶段进度，不是每个 token 的流式输出，也不是百分比估算。进度查询失败只提示同步暂不可用，不能触发重新发送聊天。整合阶段单独显示“正在整合”。

## 5. GLM 验证码处理

没有实现跳过、绕过验证接口、令牌伪造或模拟拖动滑块。新增的是可见验证控件检测和人工恢复流程：

1. 检测到 GLM 页面可见的验证码/滑块验证控件时，状态变为“等待人工验证”，暂停输入或发送；释放输入占用，让其他模型继续。
2. 点击界面“完成人工验证 · GLM”，在原模型网页亲自完成验证，不刷新、不切换模型。
3. 检测到验证界面消失后重新进行正常页面、输入、会话及接收状态核验。尚未提交则继续发送；已经提交则仅核验原请求并继续采集，不再点击一次发送。

控件消失不等于服务端验证必然成功，所以恢复仍须通过原有接收确认。验证码等待计入对应任务预算；预算到期后本轮停止，用户可明确发起新任务。检测针对现有可见 DOM/iframe 特征，排除了普通消息、代码块、输入框和隐藏控件的相关文字；站点改版、跨域控件内部细节或账号差异可能无法识别。未使用真实账号验证，不保证覆盖全部 GLM 验证形态。

## 6. 更新与验证

关闭旧父应用和 Agent，在独立目录解压本版，运行 `./run.sh`。父应用与 `desktop-agent/` 必须一并更新并重启，否则进度阶段/参数可能不匹配。原本保存在用户数据目录的配置和登录数据按原规则复用；若自己在源码目录保存了配置、工作区或任务记录，先备份再迁移，不用空目录覆盖旧数据。

源码包不含 node_modules、虚拟环境、浏览器档案、账号、测试日志或用户上传的事件日志。单独的日志回放压缩包仅用于本次问题诊断，包含实际模型正文，请作为私有资料保存。
